# Spec: WORLD WAR first playable milestone

**id:** T1   **intent:** .buildloop/intent/T1.md
**policies applied:** global CLAUDE.md (strict TS, no speculative abstraction, verify before claiming)
**status:** accepted

## Summary

A pnpm/Turborepo monorepo. A pure deterministic simulation package resolves a turn from
`(world, orders[], seed, ruleset)` to `(world', events, observations, hash)`. A React + PixiJS
client runs the simulation in a Web Worker and only ever receives a visibility-filtered
`NationView`. Three utility AIs plan from their own `NationView` and submit through the same
validator as the human. Full design: `docs/architecture.md`.

## Requirements

R1. Hex math (axial), A* with terrain costs, reachable-set search, all render-independent.
R2. Authoritative `WorldState` plus order contracts; `resolveTurn` runs the 12 named phases.
R3. Simultaneous movement as a discrete-event schedule; same-time moves resolve from a common
    snapshot; head-on, swap and contested-hex conflicts are symmetric.
R4. Combat: per-class attack/defense vs soft/hard targets, terrain, entrenchment, strength,
    organization, readiness, supply, recon, air support, morale, combined arms; structured
    results including retreats and captures; preview with a range, not a promise.
R5. Economy: credits, energy, materials, food stockpiles; industrial capacity and research as
    throughput; ledger per turn; no negative stockpiles; budget allocation; recruitment queue.
R6. Supply: Dijkstra from cities/depots over permitted territory, capacity-limited, enemy
    interdiction, priorities; affects readiness, fuel, ammunition, combat.
R7. Fog of war: visible / previously observed / unknown; last-known enemy positions; AI and
    UI read only `NationView`.
R8. AI: strategic layer (threats, objectives, recruitment, research) and tactical layer
    (orders), deterministic, legal by construction and by validation.
R9. Victory: victory-point share, last nation standing, or turn limit.
R10. Save/load: versioned, multiple slots, compatibility check.
R11. UI: top resource bar, left nav (overview/military/economy/research/diplomacy), Pixi map,
     right inspector, bottom orders/notifications/end-turn; planned vs submitted vs resolved
     are visually distinct; after-action report with jump-to-location.

## Acceptance criteria

AC1. Same inputs give the same output hash | `simulation` determinism tests
AC2. Order permutation does not change the result | `simulation` permutation test
AC3. Resources balance against the ledger and never go negative | economy tests
AC4. Movement conflicts (contest, swap, blocked) resolve symmetrically | movement tests
AC5. NationView contains no formation outside the nation's vision | fog tests
AC6. Every AI order passes validation | AI legality test
AC7. 100 seeded AI-vs-AI matches end with a winner by turn 30, no invalid state | `tests/` soak
AC8. Save round-trips to an identical hash; incompatible versions are refused | save tests
AC9. Browser journey: start, pick nation, select formation, order, end turn, report, save | Playwright
AC10. `pnpm build`, `pnpm typecheck`, `pnpm lint`, `pnpm test` all exit 0 | turbo

## Ordering surface

state-machine: the turn resolver's phase order and the same-time movement groups. Covered by
determinism, permutation and conflict tests rather than a TLA+ model: the resolver is a pure
function with no concurrency, so interleavings are fully enumerated by the explicit time
schedule. Recorded here so VERIFY can disagree.

## Policy conflicts

- Global CLAUDE.md prefers Python/FastAPI backends; the originator explicitly specified
  Fastify/TypeScript for this project. Following the explicit project request.
- shadcn/ui is "where appropriate": not used in M1; the controls are small Tailwind components.
- PostgreSQL/Drizzle are "when needed": not needed for single-player, not added in M1.

## Rejected alternatives

- Tick-per-movement-point movement: ties every unit to the same speed grid; the discrete-event
  schedule (arrival time in thousandths of a turn) handles mixed speeds and is still symmetric.
- Seeded sequential PRNG stream: results would depend on the order of draws. Instead every
  random value is a hash of `(seed, turn, phase, entity ids)`, so iteration order is irrelevant.
